# 联调延迟排查与修改记录

日期：2026-11-06。

## 已确认原因

1. 取流器已有后台读取和最新帧缓存，不是按顺序检测所有摄像头历史帧。
2. 启动流程只预热普通检测。独立测量首次跟踪检测耗时 5330.6 ms，
   同组后续调用为 14.9 到 39.5 ms。首次旅客入库后才运行跟踪时会出现冷启动停顿。
3. 原流程先取帧，再同步处理最多八条旅客图片。入库耗时计入这帧位置延迟。
4. 原预览跟随识别结果刷新。推理或入库停顿会直接表现为视频停顿。
5. 原程序完成推理后固定等待 200 ms，实际识别周期为处理耗时再加 200 ms。
6. 原预览把每个图像通过 Qt 队列发送到主线程，主线程繁忙时可能显示旧画面。
   新流程给每路画面保留一个可替换缓存，由界面定时读取。

## 修改

- 启动阶段按实际区域形状预热跟踪检测和重识别，再打开供框台视频。
- 每次至多处理一条旅客入库，入库之后重新选取最新帧。
- 按识别开始时刻安排下一帧，慢推理时跳过旧帧，不补做全部历史检测。
- 供框台 RTSP 预览独立刷新；界面每路只保留最新待显示画面。
- 新增识别结果页，展示被阈值或轨迹成熟度过滤前的候选，同时保留原有上报规则。
- 新增性能页、可选性能日志，以及识别间隔、输入尺寸、预览帧率和翻转增强设置。
- 绑定算法、身份判定阈值、完整身份编号和图像时间戳的含义保持原规则。

## 本机测量

使用同一段本地视频循环推送到回环 RTSP。闸机和供框台任务同时运行，
手动加入一张参考旅客图片，启用一个全画面供框台区域，实际加载 YOLO 和 FastReID。
供框台画面同时包含多名检测目标。使用本机 CUDA，不能代表目标服务器。

| 指标 | 修改前 90 秒 | 修改后 90 秒 |
| --- | --- | --- |
| 位置消息数 | 278 | 392 |
| 位置延迟中位数 | 141 ms | 156 ms |
| 位置延迟 95% 分位 | 328 ms | 241.2 ms |

修改后最后 30 秒的位置延迟最大值为 328 ms，没有出现随运行时间持续增长。
预览累计收到供框台图像 803 帧，识别报告 393 条。
模拟每帧推理 300 ms 的回归测试确认，识别变慢时预览仍可独立刷新。
修改前统计脚本在汇总数组时出错，表中修改前数值重新从保留的位置消息计算，
不把失败的脚本报告视为完整验证成功。

## 现场验证

现场持续 5000 ms 延迟的具体原因仍需服务器日志确认。首次跟踪冷启动已复现 5330.6 ms。
现场仍需根据性能页区分 CPU 回退、多人多区域计算、入库等待、界面等待和 MQTT 积压。
实际摄像头、网络、生产 MQTT、真实 RFID 及身份准确率仍需现场验证。
短时或回环测试不代表所有部署环境的长期表现。

后续强制 CPU 的 30 秒测试复现了持续数秒延迟：
人体检测约 180 到 230 ms，特征提取约 6156 到 9358 ms。
位置消息中位延迟 8671.5 ms，最大 9594 ms。
同期间预览仍收到 358 帧，说明预览已与慢推理分开。
这是 CPU 多人特征提取吞吐不足，不能仅靠跳帧或增大识别间隔解决。
测试时同机还有打包任务，数值只用于确认耗时集中在特征提取，不作为服务器性能承诺。
现场若显示 `cpu`，需要核查 NVIDIA 驱动及 CUDA 是否可用。
在这组多人输入下，本机 CPU 不能满足默认 600 ms 的位置有效期。

CPU 证据：`result/latency_cpu_20261106/verification.json` 及对应会话 `performance.jsonl`。
