## 启动

现有 Conda `mmpose` 环境已经补齐联合调试依赖。没有重建环境，也没有替换原项目入口。
`requirements-integration.txt` 记录额外依赖和参考版本，当前机器无需再次安装。
其他机器应先确认 PyTorch、CUDA 和 OpenCV 的兼容性；尚未验证从零重建整个环境。
Ultralytics 的依赖元数据使用 `opencv-python` 包名，本项目使用 `opencv-contrib-python`。
批量安装前应检查解析结果，避免同时安装两套提供 `cv2` 的包。

```powershell
conda run --no-capture-output -n mmpose python D:\code\mediapipe-master\pose\start_integration.py
```

其他入口：

```powershell
D:\code\mediapipe-master\pose\start_integration.cmd
conda run --no-capture-output -n mmpose python -m pose_project integrate
```

程序打开一个新设计的 PyQt5 窗口。它直接复用算法和后台任务，不打开、隐藏或嵌入原来的三个窗口。

## 重识别结果与性能调试

2026-11-06 更新：启动阶段先预热跟踪检测和重识别模型，再连接供框台视频。
RTSP 预览从最新帧独立刷新，不等待推理完成。每路预览只保留一个待显示画面，
界面忙碌时替换旧画面，不把视频逐帧排入界面事件队列。
识别线程每次最多处理一条旅客入库消息，再读取最新帧。
识别间隔从每帧开始时计算，不再在完成推理后额外等待固定的 200 毫秒。

“重识别结果”显示当前帧的区域、轨迹、候选完整旅客编号、相似度、状态和坐标。
候选包含未达阈值、轨迹确认中、已匹配和身份重复；没有旅客库时只展示检测目标。
这些调试候选不改变位置消息协议，也不把低分候选作为绑定身份发送。
结果年龄超过位置有效期后，界面清除叠加检测框，保留表格并显示已过期。
预览画面上的框来自最近一次识别，短时间内可能与正在移动的目标存在位置差。

“旅客证据”按完整旅客编号合并显示闸机抓拍、人物库身份、供框台最新匹配、
区域、轨迹、相似度和绑定结果。选择一行后，界面显示闸机上半身图、供框台当前目标裁剪图，
并列出两侧时间、坐标和绑定判定依据。这个页面用于实时查看消息链路和画面对照，
相似度仍需结合两张图片、时间和轨迹人工判断，不能单独作为身份正确的证明。

“性能调试”显示推理设备、采集及识别帧率、检测和特征提取耗时、
取帧时图像年龄、识别完成及消息接收时的位置延迟、界面接收等待、
跳帧数、旅客入库耗时与等待条数、MQTT 待发送数量及重连次数。
勾选“记录性能日志”后，每秒至多保存一条到当前会话的 `performance.jsonl`。

“现场测试”用于真实摄像头和消息服务器验证。启用后填写测试编号、记录人员、
测试地点、测试场景和说明。程序会保存每帧重识别结果、旅客入库、绑定判定、
MQTT 状态和后台错误。现场观察可以填写预期结果、实际结果、通过/失败/待核对
以及截图编号或视频时间点。现场测试记录会自动同时开启性能日志。

本功能生成两个文件：

```text
field_test.json
field_test_events.jsonl
```

`field_test.json` 保存测试信息、运行时间、配置摘要、运行环境、事件数量和会话统计。
`field_test_events.jsonl` 保存按时间排列的结构化事件。识别事件不包含视频帧和图片
编码正文，旅客图片仍按已有规则只记录消息摘要。

## 多人排队与特征缓存

2026-11-09 更新：联调界面的“区域”页，为每个供框台增加“多人排队”选项。
支持队首在下、上、左、右、最大目标，以及关闭队首筛选。
方向以旋转后的预览画面为准。旧配置未填写队首模式时，默认使用“队首:下”。
明确选择“队首:关”会保留关闭状态。调整选项后自动保存，停止并重新启动联调后生效。

- 每个区域独立维护检测跟踪和队首，只对选中的队首提取特征并匹配旅客。
- 现任队首仍在区域内时，小幅位置变化不换人。方向模式领先达到区域边长的 8%，
  或面积达到现任队首的 125% 时，才换到新的队首。
- 队首缺失时暂停识别。连续缺失达到第 8 帧，允许选择新队首。
  新轨迹仍需完成原有的三帧确认，达到匹配阈值后才输出旅客身份。
  等待期间保留空位置消息，用于清除旧位置；消息中没有旅客身份。
- 同一轨迹首次提取特征后，每隔 10 个处理帧刷新。缺少轨迹编号时逐帧提取。
  轨迹过期后清除特征缓存和轨迹分数，空画面时也会执行清理。
  已完成匹配的旅客锁定记录保留到本次会话结束。
- 新增或更新闸机旅客时，重新计算图库分数，保留队首、轨迹缓存和已确认身份。
  已确认身份在轨迹存续期间不会因为另一名旅客分数更高而改变。
- CPU 检测阶段使用 8 线程，特征提取使用 20 线程，OpenCV 使用 4 线程。
  CPU 启动状态显示“CPU 20 线程并行”。使用 GPU 时显示实际设备。

8 帧等待和 10 帧刷新均按实际处理帧计数，不按摄像头原始帧率计数。
默认每 200 毫秒识别一次时，分别约为 1.6 秒和 2 秒；推理耗时较长时会更长。
这次修改没有现场速度或识别正确率的测量结果。

现场验证时，先让两人进入同一区域，确认只显示所选方向的队首。
随后小幅挪动两人的位置，检查目标保持情况。
让队首短暂遮挡后返回，再让队首离开，分别检查等待和接替行为。
保持一人排队期间，从闸机新增另一名旅客，检查现任队首及旅客编号是否保持。
A、B 区分别验证方向，再重启程序检查选项是否恢复。

2026-11-10 更新：旅客首次完成匹配后，任务锁定到原来的区域和轨迹。
A、B 及其他区域共享这份会话记录。同一旅客不会再分配给其他目标。
队首更换、旧轨迹过期、编号复用或更新旅客图片，都不会解除锁定。
原轨迹仍有效且满足匹配条件时继续输出位置；原轨迹消失后不输出旧位置。
同一帧出现多个符合条件的目标时，暂不确认，也不按区域处理顺序选择。
没有轨迹编号的目标显示“等待稳定轨迹”，不完成匹配。
“旅客证据”显示“已匹配，任务锁定”，其他目标的候选图片不会覆盖原匹配证据。
结束并重新启动联调会创建新会话，清空上述锁定记录。
首次确认错误也会保留错误结果；锁定不代表首次身份判断一定正确。
如果跟踪器把同一有效轨迹编号交给另一人，仍需现场视频排查。

取消勾选后停止追加。终端也输出相同的简要指标。

“算法”页保留默认值：识别间隔 200 ms、检测输入 960、预览上限 15 fps、翻转增强开启。
旧配置会补齐这些默认参数。调整前停止当前会话，保存配置后重新启动。
检测输入变小或关闭翻转增强可以减少计算量，识别准确率需用现场画面复核。
识别间隔过大或推理慢于位置有效期时，绑定仍可能失败，程序不会延长有效期来掩盖延迟。
取帧时间是本机解码完成时间，无法据此测量摄像头、网络及解码前的全部缓存时间。

## 首次调试顺序

1. 为闸机选择“本地文件”或“RTSP / 网络流”，选择文件或填写地址。读取首帧，确认是否需要旋转 180°。
2. 为供框台选择文件或填写 RTSP 地址。读取首帧，确认画面方向和尺寸。
3. 在“区域”中框选闸机抓拍区。
4. 启用所需供框台区域，每个供框位只框选一个区域。
5. 确认采集条件、绑定参数，点击保存配置。
6. 点击“启动联调”。旅客图片自动进入重识别人物库。
7. 查看消息中的完整旅客编号和人员位置。
8. 在底部填写行李框 RFID，发送测试事件，检查结果及判定依据。
9. 停止后查看会话目录中的日志，再调整参数开始新会话。

更换画面尺寸时，程序按比例换算现有区域。更换摄像头或画面内容后，仍要重新标定。
工作台启动后锁定配置，修改配置前需要停止当前会话。

## 新增与删除区域

“新增供框台区域”按 A 到 Z 分配空闲编号。新区域默认启用，需完成区域框选后才能启动。
每个框旁的删除按钮删除该框。
每组“启用”选项旁的删除按钮删除整组区域，并移除对应的 RFID 测试选项。
闸机抓拍区可以独立删除和重新框选；联调启动前必须重新配置。

配置未画完时也可以保存和重新打开。启动时只检查、使用已启用的供框台区域；
已启用但缺少区域时，提示具体区域编号并阻止启动，不会静默忽略该区域。
未启用区域保留在配置中，不参与识别和绑定。

## RTSP 摄像头

两路可以同时使用 RTSP，也可以一路文件、一路 RTSP。
在“视频”页分别选择“RTSP / 网络流”，输入摄像头地址，然后点击右侧“读取首帧”图标。
例如：`rtsp://用户名:密码@192.168.1.10:554/stream`。
地址中的路径以摄像头配置为准，用户名或密码包含特殊字符时应先作 URL 编码。
粘贴完整地址后，界面自动选择网络流模式。

预览成功后标定区域，再启动联调。保存配置后，终端 `--headless` 也使用同一地址。
RTSP 优先使用 TCP，首次连接失败后尝试 UDP；断流时按原取流器的规则重连。
后台只保留最新一帧。闸机抓拍时间、供框台位置时间均来自收到画面的时刻。
这些时间不等于摄像头曝光时间。实时流忽略闸机原有的文件起始时间覆盖。
停止及关闭预览会请求退出取流，正在等待网络时需要等到底层读取超时。
连接和读取有超时限制，不使用无超时的备用打开方式。

RTSP 地址会随视频源保存在配置与会话快照中，地址内的摄像头账号密码也会一并保存。
MQTT 密码仍不保存。对外分享配置前，请移除摄像头账号密码。

## 两种连接方式

### 本机直连

默认模式，不连接 MQTT。三部分通过同一消息队列连接，消息字段仍采用既有协议。
RFID 测试事件进入同一接收流程。没有设备时，可以先检查编号、坐标和判定逻辑。

### MQTT 联调

三部分使用统一配置，所有内部人员图片、位置和 RFID 消息均通过指定服务器。
现有服务器必须提前启动。工作台不会启动或管理服务器。

| 用途 | 默认主题 |
| --- | --- |
| 旅客图片 | `check_gate/person/collected` |
| 人员位置 | `reidtest` |
| RFID 事件 | `pose/rfid` |
| 成功绑定输出 | `pose/bindings` |

四个主题必须互不相同。发布使用 QoS 1，不设置保留消息。
断开时保存有上限的待发送队列；重连后发送原消息，不修改位置时间。
停止时，日志会记录尚未发送或确认的消息数量。
“发送绑定结果”默认关闭，启用后只发送成功绑定的三个字段。
在 MQTT 模式下点击底部测试注入，会向所选服务器发送测试消息。

密码可在界面填写，或在终端设置 `MQTT_PASSWORD`。
密码不写入配置或会话快照。当前工作台不管理证书文件，仅支持系统信任链 TLS。

## 联调入口处理的接口问题

- 统一服务器与主题，保留原有独立程序的配置。
- 人物库始终使用上游完整 `passenger_id`。本地编号只用于界面显示。
- 同一旅客的新图片更新原条目。人物库最多保存 256 人。
- 人物库变化后，更新匹配数据并清除旧分数历史。保留跟踪、队首和已确认身份，复用检测模型。
- 同一身份命中多个目标时，本帧不采用该身份，并记录原因，不随意选择一个目标。
- 文件回放使用当前会话时间与视频帧位置建立时间对应，落后时跳过旧帧。
- RTSP 时间记录取流端实际收到画面的时刻，不代表摄像机曝光时刻。
- 同一画面不会因为重复发送而得到新时间。没有新画面时，不发送假的新位置。
- 画面尺寸与区域不一致时，程序明确报告错误，不自动猜测坐标。
- 每次会话单独保存采集结果和编号映射，避免复用上一轮的本地编号记录。

以上调整仅适用于新联调入口。旧独立界面的身份选择、发布节奏等行为没有全面修改。
绑定核心算法仍使用原有规则，姿态动作分类不参与绑定。

## 终端检查

```powershell
conda run --no-capture-output -n mmpose python D:\code\mediapipe-master\pose\start_integration.py --check
conda run --no-capture-output -n mmpose python D:\code\mediapipe-master\pose\start_integration.py --self-test
conda run --no-capture-output -n mmpose python D:\code\mediapipe-master\pose\start_integration.py --headless --duration 60
```

`--check` 检查当前解释器、依赖和本地模型文件。
`--self-test` 使用模拟位置消息检查绑定，不运行模型或摄像头。
`--headless` 使用已保存的配置启动真实后台任务，只输出终端日志。
按 Ctrl+C 请求停止。`--duration` 设置自动停止时间，单位为秒。

可用 `--config <完整 JSON 路径>` 指定另一份配置。
图形界面的保存按钮只写入所选联调配置，旧配置文件不变。

## 输出与验证边界

每次运行创建新目录，其中包括：

```text
settings.json       本次配置，不含密码
runtime.log         各模块日志
messages.jsonl      接收消息，图片编码只记录长度
decisions.jsonl     绑定判定、候选旅客和停留依据
summary.json        停止后的统计
gate/               抓拍图片、人员汇总与编号映射
```

启用现场测试记录后，会话目录还包括：

```text
field_test.json          现场测试元数据和会话汇总
field_test_events.jsonl  现场测试结构化事件
```

本地模型验证脚本：

```powershell
conda run --no-capture-output -n mmpose python D:\code\mediapipe-master\pose\scripts\verify_integration.py --output D:\code\mediapipe-master\pose\result\integration_verify_new
```

脚本从已有视频生成短片，运行实际采集、YOLO 和 FastReID，并检查界面与停止流程。
该检查中手动提供一张人物参考图；短片不代表闸机已经成功自动抓到对应旅客。
RFID 测试事件也不是真实硬件事件。位置过期或停留不足时，未绑定是预期保护行为。

真实摄像头、实际 RFID、现场服务器和识别正确率仍需联调。
本机同时运行多个模型时，应观察消息时间与推理耗时，不能用放宽位置有效期代替性能验证。

现场测试至少记录以下结果：

| 类别 | 需要记录的结果 |
| --- | --- |
| 闸机抓拍 | 应抓到人数、实际抓到人数、漏抓、重复抓拍、图片是否可用、完整旅客编号 |
| 人物库 | 入库时间、旅客编号、图片来源、图片是否与现场人员对应 |
| 重识别 | 区域、轨迹编号、预测身份、相似度、第二名分数、分数差、锁定状态、漏识别和误识别 |
| 跟踪 | 目标短暂遮挡后是否保持、离开后是否清除、队首切换是否正确、轨迹编号是否连续 |
