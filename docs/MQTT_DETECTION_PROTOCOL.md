# 人包绑定系统：检测端 MQTT 接口协议

版本：1.0  
日期：2026-10-22  
适用程序：`binding_app.py`、`binding_runtime.py`、`passenger_tray_binding.py`

目录整理后，界面位于 `src/pose_project/apps/`，绑定实现位于 `src/pose_project/binding/`。
启动命令为 `conda run --no-capture-output -n mmpose python -m pose_project binding`。

## 1. 接口用途

检测端持续上报各供框台区域内的旅客身份和位置。
人包绑定工作台据此计算操作区内的有效停留时间。
工作台收到读码器的推框信号后，结合 RFID 判定绑定关系。

检测端负责人员检测、跟踪、重识别和区域归属。
检测消息无需包含 RFID、放物动作标签、照片或视频。
放物动作识别结果和检测置信度也不是当前算法的必填数据。

本协议中的“完整人员列表”，指同一帧中当前区域的全部有效检测结果。
这是一项输入要求，不能据此保证检测端不会漏检。

## 2. MQTT 连接约定

| 项目 | 约定 |
| --- | --- |
| 角色 | 检测端发布消息，绑定工作台订阅消息 |
| MQTT 版本 | MQTT 3.1.1 |
| 服务器地址 | 联调时填写实际 MQTT 服务器 IP 或域名 |
| 端口 | 普通连接常用 1883；启用 TLS 时按服务器配置填写 |
| 认证 | 用户名、密码和 TLS 设置由双方约定 |
| 客户端 ID | 每个检测端使用独立且不重复的客户端 ID |
| 消息编码 | UTF-8 |
| 消息正文 | JSON 对象 |
| 发布 QoS | 1 |
| retain | `false` |
| 发送频率 | 每个区域每 200 毫秒发送一次，约每秒 5 条 |

检测消息建议使用主题 `pose/detections`。
使用这个主题时，将工作台“数据接口”中的“检测主题”同步改成 `pose/detections`。
项目当前默认主题仍是 `simulation/binding/detections`，联调时也可直接沿用。
两端必须使用相同的具体主题名称，当前工作台不支持主题通配符。

多个区域共用检测主题，通过正文中的 `roi_id` 区分。
例如有 A、B、C 三个区域时，总发送量约为每秒 15 条。

## 3. 检测消息格式

### 3.1 有人时

以下示例表示同一帧中，A 区域识别到两名旅客：

```json
{
  "roi_id": "A",
  "captured_at_ms": 1792630800000,
  "detections": [
    {
      "passenger_id": "a6deca95bec249a4b5b0124ec6348ff6-2026-10-22",
      "bbox_xyxy": [320, 255, 480, 495]
    },
    {
      "passenger_id": "c13b04a712d14c58b07182909de65420-2026-10-22",
      "bbox_xyxy": [700, 530, 860, 770]
    }
  ]
}
```

### 3.2 无人时

区域正常检测但无人时，仍按周期发送空数组：

```json
{
  "roi_id": "A",
  "captured_at_ms": 1792630800200,
  "detections": []
}
```

空数组表示“当前帧没有有效人员检测结果”。
区域有人或无人，都需要持续上报。
检测故障、摄像头断流不能伪装成正常无人；应通过独立运维渠道报告。
当前工作台尚未实现独立设备状态主题。

### 3.3 字段定义

| 字段 | 类型 | 必填 | 含义与要求 |
| --- | --- | --- | --- |
| `roi_id` | 字符串 | 是 | 供框台区域编号，单个大写字母，如 `A`、`B`、`C`；必须已在工作台配置 |
| `captured_at_ms` | 整数 | 是 | 本帧对应的 Unix 时间戳，单位为毫秒；同一条消息中的人员属于同一帧 |
| `detections` | 数组 | 是 | 当前帧、当前区域的完整有效人员列表；无人时为 `[]` |
| `detections[].passenger_id` | 字符串 | 是 | 稳定旅客身份，格式为“32 位随机字段-YYYY-MM-DD” |
| `detections[].bbox_xyxy` | 数值数组 | 是 | 检测框 `[左, 上, 右, 下]`，使用约定图像中的像素坐标 |

同一帧中的每名旅客各占一个数组元素。
同一条消息中，`passenger_id` 不能重复。
每条消息只包含一个区域；同一帧的 A、B 区域分别发送，使用相同图像时间。
JSON 正文直接采用上述格式，无需添加离线回放文件中的 `topic` 和 `received_at_ms`。
MQTT 主题通过发布参数指定，本端自行记录接收时间。

## 4. 旅客身份要求

推荐格式：

```text
<32位小写十六进制随机字段>-<首次确认身份的日期>
```

随机字段可采用去掉连字符后的 UUIDv4，生成端负责防止身份冲突和编号复用。
日期采用双方约定的本地日期，本项目使用北京时间。
供框台区域已通过 `roi_id` 单独传递。

检测端应满足：

1. 同一旅客在连续帧中保持相同 ID。
2. 短暂遮挡或离开后，重识别成功时复用原 ID。
3. 同一旅客连续使用多个行李框时，保持相同 ID。
4. 旅客跨区域时，保持相同 ID，通过 `roi_id` 表示所在区域。
5. 旅客跨午夜仍在跟踪时，保留首次身份日期。
6. 不同旅客使用不同 ID，禁止将回收后的跟踪序号直接作为旅客 ID。

工作台也兼容旧格式 `A-<32位随机字段>-YYYY-MM-DD`。
新对接推荐采用独立区域字段和不带区域前缀的旅客 ID。
跟踪身份变化会分割停留记录，因此不能每次上报都生成新 ID。

## 5. 坐标约定与静态配置

坐标原点位于约定图像的左上角。
X 轴向右，Y 轴向下，单位为像素。
发送端应保证 `0 <= 左 < 右 <= 图像宽度`，以及 `0 <= 上 < 下 <= 图像高度`。
坐标可以是整数或有限小数，禁止 `NaN`、无穷大和字符串坐标。

检测端和工作台必须使用同一图像尺寸及坐标方向。
模型若使用缩放、补边或裁剪图像，应先将检测框换算到约定图像。
修改分辨率、裁剪范围或摄像头位置后，需要同步重新标定区域。

当前算法使用检测框中心，判断旅客是否处于操作区。
仅看到上半身时，上报实际的上半身检测框即可。
操作区也应按上半身框中心标定，无需估计脚部坐标。

以下资料在联调前一次性提供，在工作台中配置：

| 资料 | 用途 |
| --- | --- |
| 检测设备或摄像头编号 | 明确每个区域的数据来源 |
| 图像宽度、高度与一张标定示例图 | 统一像素坐标 |
| 各供框台区域编号及区域坐标 | 配置 `roi_xyxy` |
| 各区域的操作区坐标 | 配置 `operation_roi_xyxy` |
| 旅客归属区域的判定规则 | 避免双方对区域边界的理解不同 |
| 采集时间的记录方式 | 核对时间是否包含取流、解码或推理延迟 |
| MQTT 地址、端口、主题和认证方式 | 完成网络接入 |

上述设备信息和几何配置无需在每条检测消息中重复发送。
当前程序不依据额外的 `camera_id`、图像尺寸字段自动区分相机或换算坐标。
一个区域应由约定的单一数据源提供完整列表；多相机结果需要先融合。

## 6. 时间、频率与异常处理

### 6.1 图像时间

`captured_at_ms` 表示图像对应的时间，不应在推理或 MQTT 发送完成后重新赋值。
例如，示例中的 `1792630800000` 对应北京时间 `2026-10-22 09:00:00`。
禁止发送秒级时间戳、格式化日期字符串或未经换算的视频相对时间。

优先使用已换算到系统时间的相机采集时间。
若只能在检测端收到图像时记录时间，应明确告知这一口径，并实测取流延迟。
工作台无法仅凭消息内容恢复相机中的积压时间。

检测端和工作台分机部署时，应使用同一校时源。
当前程序要求图像时间不晚于本端接收时间，发现未来时间会记录输入错误。
联调时应检查两端时钟偏差，尤其是网络延迟较低的场景。

### 6.2 更新和传输

每个区域建议每 200 毫秒发送一份新的检测结果。
检测逐帧执行时可按此频率抽样，检测隔帧执行时也要保持足够的有效更新频率。
同一帧重发时保留原时间和 ID，禁止给旧框换时间以维持表面更新。
同一区域、同一图像时间的重发，应保持人员列表和检测框一致。

当前实验配置中，最大有效采样间隔为 600 毫秒，位置有效期也是 600 毫秒。
这两个值是算法配置项，不能将 600 毫秒作为期望发送周期。
检测端应及时发送最新结果，断线后不批量补发过期位置数据。
网络及推理延迟需要实测，再共同确定等待时间和坐标有效期。

QoS 1 可能出现重复交付。
发送端不要因传输重试生成新旅客 ID，或修改原始图像时间。
当前接收端会过滤可识别的 MQTT 重传，同一采集时间也不会重复增加停留时间。
MQTT 传输确认仅表示传输进展，不表示绑定判定成功。
当前检测接口没有单独的业务确认主题，格式错误在工作台运行记录中显示。

## 7. RFID 及绑定结果的边界

检测端按前述格式提供人员数据即可。
RFID 由读码器接入端在光电触发后，通过独立 RFID 主题发送：

```json
{
  "roi_id": "A",
  "rfid": "RFID-A-0001",
  "event_id": "reader-A-20261022-000001"
}
```

RFID 主题使用工作台配置的具体名称，当前默认是 `simulation/binding/rfid`。
`event_id` 为可选字段，建议提供，用于同一会话内过滤重复推框事件。
同一次触发重发时保持事件编号，下一次触发使用新编号。
RFID 不要求硬件时间戳；当前工作台以收到 RFID 消息的本机时间作为参考。
这个时间包含读码器接入和 MQTT 传输耗时，现场需核对实际延迟。

成功绑定通过独立结果主题输出，默认是 `pose/bindings`：

```json
{
  "roi_id": "A",
  "passenger_id": "a6deca95bec249a4b5b0124ec6348ff6-2026-10-22",
  "rfid": "RFID-A-0001"
}
```

检测输入、RFID 输入和绑定结果必须使用三个不同主题。
未绑定和多人封存事件保留在工作台记录中，当前不发送成功绑定消息。

## 8. 联调检查

1. 工作台选择“MQTT 订阅”，填写实际服务器和两个输入主题。
2. 检测端每 200 毫秒上报完整列表，检查工作台中的区域和人员框。
3. 同一旅客停留、短暂遮挡及再次识别时，检查 ID 是否稳定。
4. 区域无人时检查空数组消息；断流时检查独立故障报告。
5. 检查两端图像尺寸、标定区域、时间戳单位和时钟偏差。
6. 配合真实光电与 RFID 触发，核对返回的区域、旅客 ID 和 RFID。

验收时分别记录数据是否符合协议，以及真实业务中的绑定正确率。
发送成功或模拟数据通过，不能代替现场绑定效果验证。
